# 2. PRINCIPI TECNICI FCTO — 15 Pilastri

> Un Fractional CTO non scrive codice. Ma deve capirlo meglio di chi lo scrive. Deve vedere i pattern dove gli altri vedono file. Deve sentire il rischio dove gli altri vedono "funziona".

**Macro-framework — "CRAFT":**

| Lettera | Area | Sezioni | Domanda guida |
|---------|------|---------|---------------|
| **C** | Costruire | 1–3 | "Cosa stiamo costruendo e come?" |
| **R** | Ratificare (Verificare) | 4–6 | "Come sappiamo che funziona?" |
| **A** | Assicurare (Proteggere) | 7–9 | "Come lo proteggiamo?" |
| **FT** | Far funzionare il Team | 10–15 | "Come facciamo funzionare le persone?" |

## 2.1 Architettura — mnemonica "TIFABC"

**T**rade-off · **I**ntelligence (Fitness) · **F**ossili (ADR) · **A**rea (Bounded Context) · **B**abel (Conway) · **C**ompatto (Modular Monolith)

| Concetto | Frase chiave | Azione FCTO |
|----------|-------------|-------------|
| **Trade-off espliciti** | "Non esiste giusto, esiste adatto" | Quale qualità sacrifico per quale altra? |
| **Fitness Functions** | "Se non puoi misurarlo, non esiste" | 3–5 su dove il team già sbaglia |
| **ADR** | "Folklore = debito. Se non è scritto, non è stato deciso." | Il FCTO insegna al team — non scrive tutti gli ADR |
| **Bounded Context** | "Stessa parola, significato diverso = confine" | Progetta dai linguaggi del business, non dalle tabelle |
| **Conway's Law** | "Architettura = specchio dell'orgchart" | Cambia la comunicazione prima del codice |
| **Modular Monolith** | "Non estrarre finché il confine non esiste già" | Team < 10? Dominio instabile? → Monolite modulare |

**Formato ADR minimo:**
```
# ADR-NNN: Titolo
## Status: Accepted | Deprecated | Superseded by ADR-XXX
## Date: YYYY-MM-DD
## Context: Cosa richiedeva una decisione
## Decision: Cosa abbiamo deciso
## Consequences: Cosa cambia — positivo E negativo
```

**Quando estrarre microservizi:** solo quando il confine esiste GIÀ nel codice + dominio + dati + team. Serve scalare indipendentemente. Serve deployare indipendentemente. Il costo operativo è sostenibile.

## 2.2 Design di Sistema — mnemonica "FIAFE"

**F**allirà · **I**dempotente · **A**sincrono · **F**allback · **E**xternal (API)

**4 Principi del Distribuito:**
1. Ogni chiamata remota **fallirà** — non SE ma QUANDO
2. **Idempotenza** è un salvavita — 1 volta o 5 = stesso risultato
3. Preferisci **asincrono** — sincrono = nemico della scala
4. Il **fallback** non è opzionale — "X è down. E adesso?"

**Trio di Resilienza — T-R-C** (ordine composizione: B-T-R-C):
```
Bulkhead → Timeout → Retry (expo backoff) → Circuit Breaker
```

**CAP Theorem (pratico):** la rete si partiziona sempre → scelta reale è CP (consistenza forte) vs AP (sempre disponibile, stale data possibile). Domanda: "Il business tollera dati di 3 secondi fa?"

**Event-Driven — quando SÌ:** emittente non sa chi ascolta, ordine non critico, team disaccoppiati, semantica temporale. **Quando NO:** risposta sincrona immediata, orchestrazione stretta, team senza esperienza con eventual consistency, no observability sulle code.

**API Design — non negoziabili:**
- API-First: contratto (OpenAPI) prima del codice
- Versioning nel path (`/v1/`, `/v2/`) — mai breaking change senza nuova versione
- Errori RFC 7807 (`application/problem+json`)
- No PII in URL (finiscono nei log, CDN, browser history)
- Paginazione server-driven

## 2.3 Qualità Software — mnemonica "SCCK"

**S**OLID (SRP+DIP) · **C**lean (dipendenze verso interno) · **C**oupling/Cohesion · **K**ISS/YAGNI

| Principio | Test rapido | Red flag |
|-----------|-------------|----------|
| **SRP** | "Descrivi senza usare 'e' o 'oppure'" | 1 feature = 8+ file in 4+ directory |
| **DIP** | "Puoi testare senza avviare l'intero sistema?" | Repository SQL hard-coded nella business logic |
| **Clean Architecture** | "La business logic sa del framework?" | Logica di pricing dentro il controller HTTP |
| **Low coupling** | File modificati per 1 feature | > 8 file = coupling fuori controllo |
| **KISS/YAGNI** | "Quale problema SPECIFICO risolvi OGGI?" | "Costruiamo un framework generico per..." |

**Clean Architecture — regola delle dipendenze:**
```
Frameworks/Drivers         ← cambia spesso
Interface Adapters
Use Cases / Application
Entities / Domain          ← cambia raramente
```
Le dipendenze puntano sempre verso l'interno. Business logic non sa nulla di HTTP, DB, framework.

## 2.4 Testing — mnemonica "CPCT"

**C**overage ≠ fiducia · **P**iramide · **C**ontratto · **T**estabilità = architettura

**Piramide:**
```
           /\
          /  \    E2E (pochi, stabili, business-critical)
         /----\   Integration (medi, confini reali)
        /------\  Unit (molti, veloci, logica dominio)
       /--------\ Contract (obbligatori tra team indipendenti)
```

**Errore classico:** 500 unit test su getter/setter + 0 integration test sul DB = coverage alto, fiducia zero.

**Principi:**
- Testa il comportamento, non l'implementazione (se il test si rompe dopo refactoring senza cambio comportamento = accoppiato)
- Integration test > unit test superficiali in sistemi business-critical
- Contract test obbligatori se team diversi rilasciano indipendentemente
- Se testare è difficile → la logica è nel posto sbagliato (problema architetturale)

**TDD — quando ha senso:** logica complessa, codice critico (pagamenti, compliance), design. Non serve per CRUD semplice, glue code, prototipi.

## 2.5 Delivery e CI/CD — mnemonica "DRIFT"

**D**eploy ≠ Release · **R**ollback < 5 min · **I**n < 10 min (feedback) · **F**eature flags · **T**runk-based

> Deploy è un evento tecnico noioso. Release è una decisione di prodotto.

**Pipeline ideale:**
```
Commit → Lint → Test → Build → Security Scan → Deploy Staging → Deploy Prod
         └── Feedback in < 10 minuti ────────────────────────────────────────┘
```

**Non negoziabili:**
- Trunk-based development (branch > 3 giorni = debito)
- Green build = deployable sempre
- Niente deploy manuali via SSH
- Rollback < 5 minuti
- SAST + dep scan + secret detection in CI — non afterthought

**Feature Flags:** deploy incompleto (sempre green), rilascio graduale (1%→10%→50%→100%), kill switch istantaneo, A/B testing. Attenzione: devono avere data di scadenza.

## 2.6 Osservabilità — mnemonica "LMT + LTES"

**L**og · **M**etriche · **T**race (3 pilastri) + **L**atency · **T**raffic · **E**rrors · **S**aturation (Golden Signals)

> In produzione non hai il debugger. Log, metriche e trace sono i tuoi unici strumenti reali.

**Golden Signals:**

| Signal | Misura | Alert se |
|--------|--------|----------|
| Latency | P50, P95, P99 | P99 > SLO per 5 min |
| Traffic | Request rate | Drop improvviso > 50% |
| Errors | % risposte 5xx | Error rate > 1% |
| Saturation | CPU, RAM, conn DB | > 80% per 10 min |

**Principi logging:** JSON strutturato su stdout · mai PII · Correlation ID obbligatorio · log il "perché" non il "cosa" · WARN/ERROR in produzione.

**SLA/SLO/SLI:** SLI = metrica misurata; SLO = target interno; SLA = promessa contrattuale. Definisci SLO PRIMA di un incidente.

## 2.7 Sicurezza — mnemonica "LDZF + OWASP"

**L**east Privilege · **D**efense in Depth · **Z**ero Trust · **F**ail Secure

> Quando qualcosa va storto, il default è NEGARE accesso.

**OWASP Top 10 sintetico:**

| # | Vulnerabilità | Contromisura |
|---|---------------|-------------|
| 1 | Broken Access Control | RBAC/ABAC, test autorizzazione |
| 2 | Cryptographic Failures | TLS everywhere, bcrypt/argon2 |
| 3 | Injection | Prepared statements, ORM, input validation |
| 5 | Security Misconfiguration | Hardening automatizzato, no default credentials |
| 6 | Vulnerable Components | Dep scanning CI (Snyk, Trivy) |
| 7 | Auth/Identity Failures | MFA, session timeout, rate limiting |
| 10 | SSRF | Whitelist URL, no user-controlled redirects |

**Il FCTO assicura 4 cose:** (1) threat modeling su feature critiche; (2) SAST + dep scan + secret detection in CI; (3) processo incident response documentato; (4) credenziali mai nel codice/log/env.

## 2.8 Dati — mnemonica "PVM-N"

**P**ostgreSQL default · **V**ersionare schema · **M**igrazioni backward-compatible · **N**+1 killer

**Framework decisionale DB:**

| DB | Quando |
|----|--------|
| PostgreSQL | Default ragionevole per 90% dei casi PMI. Schema fisso, relazioni, ACID. |
| MongoDB | Schema flessibile, evoluzione rapida |
| Redis | Cache, bassa latenza, key-value |
| Neo4j | Navigazione relazioni N-hop |

**Migrazioni:** sempre versionare (Flyway/Liquibase) · forward-only · backward-compatible (la vecchia versione deve funzionare durante blue/green) · separare DDL da DML pesante.

**N+1:** log con > 10 query per request = N+1 nascosto. Fix: JOIN o eager loading, sempre.

## 2.9 Scalabilità — mnemonica "VCL"

**V**erticale prima · **C**ache 80/20 · **L**oad test 2x

**Regola:** scala verticalmente finché costa meno dell'engineering per lo scale-out. Per una PMI con 1000 utenti, server più grosso = 50 EUR/mese. Scale-out engineering = settimane.

**Cache 80/20:** il 20% delle query genera l'80% del traffico. Cachare quelle riduce il carico del 60–80%. **Attenzione:** cache = causa #1 di bug in prod ("dato vecchio"). Ogni cache deve avere strategia di invalidazione chiara.

**Load test:** identifica picco atteso → testa a 2x → misura latency P99, error rate, CPU/RAM → se P99 > SLO al 2x risolvi PRIMA del lancio.

## 2.10 Team — mnemonica "TCDI"

**T**opologies · **C**ognitive Load · **D**eveloper Experience · **I** hiring

**4 Team Types (Team Topologies):**
- **Stream-aligned:** delivera valore al business (Team Checkout, Team Search)
- **Enabling:** aiuta altri team a migliorare (Team DevOps, Team Architecture)
- **Platform:** self-service per tutti (Team Infra, Team Auth)
- **Complicated subsystem:** complessità isolata (Team ML, Team Payments)

**Cognitive Load — segnali di sovraccarico:** "Chi sa come funziona X?" quotidiano · code review > giorni · onboarding > mesi · "nessuno tocca quel modulo". **Fix: semplifica il sistema, non aggiungere documentazione.**

**Developer Experience (DX) — frizioni critiche:**

| Frizione | Fix |
|----------|-----|
| Setup locale > 30 min | Docker compose / devcontainer |
| CI/CD > 20 min | Parallelizza, cache aggressiva |
| Code review > 48h | Regola: review entro 4 ore lavorative |
| Deploy manuale | Automatizza al 100% |

## 2.11 Debito Tecnico — mnemonica "Q15C"

**Q**uadrante (4 tipi) · **15**% ogni sprint · **C**omunica al business

**Quadrante Fowler:**

| | Deliberato | Inavvertito |
|-|------------|-------------|
| **Prudente** | "Sappiamo, sistemiamo dopo" | "Ora sappiamo come farlo meglio" |
| **Imprudente** | "Non abbiamo tempo per X" | "Cos'è il layering?" |

**Regola 15%:** ogni sprint riserva il 15% al debito. Non negoziabile — è manutenzione.

**Priorità:** (1) blocca feature → risolvi subito; (2) codice modificato spesso → alto ROI; (3) codice stabile → lascia stare.

**Come comunicarlo al business:** NON dire "debito tecnico". DI': "Se non facciamo questa manutenzione, la prossima feature costerà 3x e avrà il 40% di rischio di incidente."

## 2.12 AI Engineering — mnemonica "SEC-R"

**S**istema non demo · **E**val prima · **C**ost routing · **R**ischi (5)

| Aspetto | Demo | Produzione |
|---------|------|-----------|
| Input | Pulito, preparato | Rumoroso, imprevedibile |
| Output validation | "Sembra giusto" | Schema enforcement + guardrail |
| Fallback | Non esiste | Obbligatorio |
| Costo | Irrilevante | Critico (10x il budget se non controllato) |
| Evaluation | "Provalo tu" | Golden dataset + metriche automatiche |

**Cost Routing — 3 tier:**

| Tier | Uso | Costo relativo |
|------|-----|---------------|
| Haiku/Mini | Classificazione, routing, tool call semplici | 1x |
| Sonnet/Medium | Generazione, analisi, coding | 10x |
| Opus/Large | Decisioni critiche, ragionamento complesso | 50x |

**RAG:** retrieval prima di generazione. Non aggiungere testo infinito al prompt — recupera il contesto rilevante con precisione.

**5 Rischi AI:** Prompt injection · Data leakage · Hallucination · Cost explosion · Over-trust

**Human-in-the-loop per decisioni ad alto rischio.** L'AI raccomanda, l'umano decide. Mai delegare decisioni irreversibili senza supervisione.

## 2.13 Decisioni — mnemonica "R-I-F"

**R**eversibile → decidi ora · **I**rreversibile → ADR + dati · **F**ramework > decisioni

**Framework:**

```
       Reversibile        Irreversibile
   ┌──────────────────┬──────────────────────┐
B  │  DECIDI ORA,     │  ADR +               │
a  │  itera           │  DECIDI CON DATI     │
s  ├──────────────────┼──────────────────────┤
s  │  DECIDI ORA,     │  OPZIONI + TRADE-OFF │
A  │  delega al team  │  AL CEO              │
l  └──────────────────┴──────────────────────┘
```

## 3.3 AI Platform (STUDY-AI-Platform)

**Architettura a 7 layer:**
1. **Traefik** — SSL termination, routing, load balancing
2. **API Gateway** (Hono) — auth, tenant resolution, rate limiting, RFC 7807
3. **Services** — chat, knowledge, agents, integrations (BullMQ)

**Multi-tenancy:**
- PostgreSQL: shared DB, `tenant_id` su ogni riga (row-level security)
- Qdrant: collection `kb_{tenant_id}` per tenant
- Redis: prefix `aia:{tenant_id}:` per chiavi
- Risoluzione: header `X-Tenant-ID` (dashboard) o subdomain (client)

**RAG Pipeline completa:**
1. Preprocessing: estrazione testo (PDF/DOCX/TXT/web), cleaning, normalizzazione
2. Chunking ricorsivo (1000 chars, 200 overlap) o per tipo documento
3. Embedding (Qwen text-embedding-v3 via DashScope)
4. Storage: Qdrant (vettori) + PostgreSQL (metadati + full-text)
5. Retrieval: hybrid search (vector + keyword) + metadata filtering
6. Reranking: cross-encoder per qualità
7. Generation: LiteLLM routing + system prompt + context injection

**KB ibrida Vector + Graph:**
- **Qdrant:** similarità semantica, ricerca fuzzy, filtering per tipo/data/fonte
- **Neo4j:** relazioni tra entità (prodotto → fornitore → contratto), navigazione N-hop, pattern complessi
- **Fusione:** query Qdrant + Neo4j in parallelo, merge risultati ponderato

**Scelte ADR principali:**
- Neo4j vs Memgraph: Neo4j Community vince per Cypher maturo, community, stabilità. Memgraph escluso (RAM-intensive, Cypher incompleto).
- Self-hosted Hetzner EU vs cloud: GDPR + data residency + costo 10x inferiore
- Multi-model routing: non lock-in su singolo provider, riduzione costi 40–60%

## 3.5 Architettura Software (STUDY-Arch)

**Scaling — 3 tipi distinti:**
- **Tecnico:** ottimizzazione codice, caching, query, async
- **Architetturale:** decomposizione sistema (monolite → modulare → microservizi)
- **Organizzativo:** team topology, Conway's Law, cognitive load

**Architecture Assessment — 4 dimensioni:**
1. Qualità del codice (coupling, cohesion, test coverage, debt)
2. Operatività (CI/CD, osservabilità, SLO, sicurezza)
3. Scalabilità (performance, caching, load balancing)
4. Processo (delivery cadence, team structure, ADR history)

**Strangler Fig Pattern (migrazione monolite → microservizi):**
1. Identifica i bounded context nel monolite esistente
2. Costruisci il nuovo servizio accanto (non dentro)
3. Reindirizza gradualmente il traffico (1% → 10% → 100%)
4. Rimuovi il codice vecchio solo dopo migrazione completa

**Pattern Database:**
- Read replicas per query-heavy
- CQRS: scritture e letture su modelli separati
- Event Sourcing: store di eventi immutabili (rebuild state in any point)
- Sharding: distribuzione dati per chiave (solo quando necessario davvero)

**Resilienza — checklist minima:**

| Pattern | Configurazione tipica |
|---------|----------------------|
| Timeout | 500ms API esterne, 2s operazioni DB |
| Retry | 3 tentativi, exp backoff (1s/2s/4s), jitter |
| Circuit Breaker | Apre dopo 5 errori in 60s, reset dopo 30s |
| Bulkhead | Max 20 chiamate concorrenti a servizio X |
| Idempotency key | UUID per ogni operazione critica |
| Dead Letter Queue | Per messaggi non processabili dopo N retry |

## 4.2 Stack Tecnologico

| Layer | Tecnologia | Motivo |
|-------|-----------|--------|
| API Framework | **Hono** (TypeScript) | 10x Express, TypeScript-native, Bun-ready |
| ORM | **Drizzle** | Type-safe, leggero, SQL raw escape hatch |
| Frontend | **React 19 + Vite 6 + Tailwind 4 + shadcn/ui** | Veloce, moderno, owned components |
| Auth | **Better Auth** | Flessibile, Hono-compatible |
| State | **Zustand + TanStack Query** | Server state separato, client state locale |
| Router | **TanStack Router** | Type-safe routing |
| LLM Proxy | **LiteLLM** (Docker) | Multi-model, cost tracking built-in |
| Vector DB | **Qdrant** (Docker) | Veloce, HNSW, filtering avanzato, self-hosted EU |
| Graph DB | **Neo4j Community** | Standard de facto, Cypher maturo (Fase 4) |
| Queue/Jobs | **BullMQ** (Redis) | Retry, concurrency, dead-letter |
| DB | **PostgreSQL 16 + pgvector** | Multi-tenant, ACID, vector search |
| Hosting | **Hetzner CX41** | EU, GDPR, 4 vCPU, 16GB RAM, ~40 EUR/mese |
| Website | **Astro 5 + TinaCMS + Vercel** | Statico, SEO, editing online, costo 0 |

**Regole codice non negoziabili:**
- TypeScript strict mode — nessun `any`, nessun `as` non giustificato
- ESM only — no CommonJS
- Zod per validazione runtime su tutti i boundary
- Result pattern per errori attesi, eccezioni per errori eccezionali
- Tenant isolation — ogni query DEVE filtrare per `tenant_id`
- Tutte le chiamate LLM via LiteLLM — mai provider direttamente
- Token tracking obbligatorio
- Timeout + retry su ogni chiamata esterna
- Mai loggare PII o API key
